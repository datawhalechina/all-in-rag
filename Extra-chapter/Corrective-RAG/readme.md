# CRAG 论文精读：检索结果不可靠时，RAG 如何纠偏

> 本文聚焦 Yan 等人的论文版 Corrective Retrieval Augmented Generation（CRAG，arXiv:2401.15884），补充课程“校正检索”部分对原论文机制、实验和代价的拆解。配套程序只演示路由逻辑，不是论文实现，也不调用真实搜索服务。

## 一分钟看懂

普通 RAG 通常把检索器返回的 Top-k 文档直接交给生成模型。检索结果若偏题，更多上下文可能反而把答案带偏。CRAG 在检索器和生成器之间增加轻量评估器，先逐篇判断文档与问题是否相关，再据此选择内部精炼、外部搜索或两者并用。

~~~mermaid
flowchart TD
    Q[问题 q] --> R[检索器：Top-k 文档 D]
    R --> E[评估器：逐篇计算 E(q, dᵢ)]
    E --> C{整体分数与阈值}
    C -->|Correct| I[拆分、筛选、重组知识片段]
    C -->|Incorrect| W[改写查询、外部搜索]
    C -->|Ambiguous| B[内部精炼 + 外部搜索]
    I --> G[生成器]
    W --> G
    B --> G
~~~

CRAG 的关键改动不是换一个更大的生成模型，而是在生成前增加一个明确的纠偏决策点。

## 1. 问题：检索器给出的 Top-k 不等于可信证据

标准 RAG 把“检索到了内容”当作“找到了可用证据”。但向量相似度或关键词命中只是在当前索引中排序；它不能保证文档真的回答了问题，也不能保证长文档里的每一段都相关。

这会带来两层噪声：

- **文档级噪声**：整篇候选文档与问题无关，或只在表面词汇上相似。
- **片段级噪声**：文档总体有用，但夹杂无关段落；整篇塞进上下文会浪费窗口并干扰生成。

CRAG 分别处理这两层：先评估检索结果质量，再对可用文档做细粒度知识精炼。

## 2. 方法：评估、分流、精炼

### 2.1 逐篇评估，再做三路判断

对问题 q 和每篇候选文档 dᵢ，评估器给出相关性分数 sᵢ = E(q, dᵢ)。论文按上、下阈值 τ_high 与 τ_low 分流：

- **Correct**：至少一篇文档分数高于 τ_high。保留内部检索结果，但还要筛掉文档内的无关片段。
- **Incorrect**：所有文档分数都低于 τ_low。丢弃这批内部结果，改写查询后搜索外部网页。
- **Ambiguous**：不满足前两种情况。对内部结果做精炼，同时补充外部搜索结果。

~~~text
if max(scores) > τ_high:
    Correct
elif max(scores) < τ_low:    # 等价于每篇文档都低于下阈值
    Incorrect
else:
    Ambiguous
~~~

等于阈值时落入 Ambiguous。论文实现中的分数范围是 -1 到 1；它不是校准后的“答案正确概率”，不能直接读成可信百分比。上下阈值需要结合数据集设定，论文也采用经验阈值。

### 2.2 三条路径各做什么

| 判断 | 内部检索结果 | 外部搜索 | 交给生成器的知识 |
| --- | --- | --- | --- |
| Correct | 拆成知识片段，用同一评估器过滤，再按原顺序重组 | 不触发 | 精炼后的内部知识 |
| Incorrect | 丢弃 | 将问题改写成搜索词，抓取并筛选网页内容 | 外部知识 |
| Ambiguous | 精炼内部知识 | 同时搜索并筛选 | 内外部知识合并 |

外部搜索是知识源扩展，不是事实核验的终点。论文指出网页可能带来偏见或不可靠内容，因此会优先选择较权威、受规范管理的网页，并继续用评估器筛选。生产系统仍应保留来源、时间和引用链，并按业务要求审核来源质量。

### 2.3 评估器从哪里来

论文用 T5-large 初始化检索评估器，模型规模约 0.77B，并在 PopQA 相关数据上微调。论文描述的构造方式是：用问题对应的维基百科主题页作为高质量正样本线索，再从检索结果中采集相似但不相关的负样本。推理时，问题和每篇文档组成一对，评估器逐对打分。

这说明“轻量”不等于“零成本”：仍需评估器训练数据、微调过程和阈值校准。论文附录列出的 PopQA 与 Biography 阈值不同，也说明不能把一组阈值原样套到所有语料和领域。

## 3. 和课程内容、相邻方法的关系

课程第 4 章的[检索进阶技术](../../docs/chapter4/15_advanced_retrieval_techniques.md)已经介绍 RRF、重排、压缩和校正检索；[查询重构与分发](../../docs/chapter4/14_query_rewriting.md)解释查询改写与路由。本文把两部分连起来：CRAG 先诊断检索质量，只有判断内部结果不足时才触发外部搜索，并改写搜索词。本文补充原论文中的评估器训练、阈值决策、知识片段处理和实验数据。

它也和第 7 章的高级架构相关，但解决的层次不同：

| 方法 | 主要改变 | 适合回答的问题 |
| --- | --- | --- |
| 标准 RAG | 检索后直接生成 | 检索结果是否足够？标准流程默认继续生成 |
| CRAG | 增加一次检索质量评估和固定纠偏分流 | 这批文档是否值得用？该补外部知识吗？ |
| Graph RAG | 将实体、关系、路径或子图纳入知识组织与检索 | 问题是否需要跨实体关系或多跳结构化证据？ |
| Agentic RAG | 由 Agent 规划步骤、选择工具并依据反馈迭代 | 问题是否需要多轮检索、动态决策和反思？ |

课程的[知识图谱 RAG](../../docs/chapter7/20_kg_rag.md)改变知识表示和检索对象；[Agentic RAG](../../docs/chapter7/21_agentic_rag.md)允许更灵活的多步工具编排。论文版 CRAG 是基于评估分数的一次分流流程，不会自动构建图谱，也不是开放式 Agent 循环。系统可以把 CRAG 作为 Agent 的检索质量工具，但两者并非同一个概念。

## 4. 关键数字：只在论文实验设置内解读

在论文使用 SelfRAG-LLaMA2-7B 生成器的实验中，同一数据集上比较 RAG 与 CRAG：

| 数据集 | 指标 | RAG | CRAG | 差值 |
| --- | --- | ---: | ---: | ---: |
| PopQA | Accuracy | 52.8 | 59.8 | +7.0 个百分点 |
| Biography | FactScore | 59.2 | 74.1 | +14.9 个百分点 |
| PubHealth | Accuracy | 39.0 | 75.6 | +36.6 个百分点 |
| ARC-Challenge | Accuracy | 53.2 | 68.6 | +15.4 个百分点 |

这些是特定数据集、检索结果、生成器和评估设置下的论文结果，不能外推成“CRAG 在所有 RAG 项目上都会提升这么多”。不同数据集的任务和指标也不同，横向比较差值没有意义。

论文还报告了 PopQA 上每个样本的生成阶段耗时估计：RAG 约 0.363 秒，CRAG 约 0.512 秒。作者明确说明这是粗略的生成阶段开销，**不含检索和数据处理**；真实端到端系统还要计算评估器推理、网页搜索、抓取、过滤和网络等待时间。因此部署前应分别记录三条路由的命中比例、端到端延迟、外部搜索费用和答案引用质量。

## 5. 最小可运行示例

配套脚本 <code>code/crag_toy.py</code> 只用 Python 标准库。它用词项重合率代替学习到的评估器，用固定 Mock 搜索结果代替真实 Web API，演示 Correct、Incorrect 和 Ambiguous 三条分支：

~~~bash
python code/crag_toy.py
~~~

预期输出显示三类输入分别得到 1.000、0.000 和约 0.667 的词项重合分数，并进入对应分支。示例还展示 Correct 路径如何保留相关句子，以及 Ambiguous 如何合并内部片段与 Mock 外部结果。

这个示例**不复现**论文的 T5-large 评估器、检索器、真实网页搜索、生成器或论文指标；它只帮助读者核对分流规则和数据流。完整实验需要按[论文代码仓库](https://github.com/HuskyInSalt/CRAG)准备 Python 3.11 环境、模型权重与数据；外部搜索流程还需要相应 API 配置。

## 6. 适用边界与落地检查

CRAG 更适合“内部知识库有时能答、有时覆盖不足，并且允许接入可追溯外部来源”的系统。若问题涉及封闭数据、敏感资料或政策禁止联网，Incorrect/Ambiguous 路径就不能直接访问公共搜索；可以改接经过授权的企业知识源，或降级为澄清问题/拒答。

接入前建议验证以下事项：

1. **评估器是否适配本领域**：通用问答上训练的相关性判断，未必能识别企业术语、表格结构或版本差异。
2. **阈值是否经过验证**：在留出的查询集上统计误判和三路比例；重点检查“把错误文档判为 Correct”的案例。
3. **外部结果是否可追溯**：保存 URL、抓取时间、片段来源，并检查网页质量；CRAG 本身不保证网页内容真实。
4. **成本是否可接受**：统计评估器、搜索 API、抓取和生成的分项耗时与费用，设置超时、缓存和降级策略。
5. **结果是否支持拒答**：内部与外部来源都不足时，不要强迫生成器编造答案；应允许澄清或拒答。
