## 一、文本分块

> 对应章节：[第二章第二节 文本分块](../../docs/chapter2/05_text_chunking.md)

### Q1 🟢 为什么 RAG 要做文本分块？块是不是越大越好？

**参考答案要点：**

- 硬性原因：embedding model 有输入长度上限（比如 `bge-base-zh-v1.5` 只有 512 token），超长文本会被截断，向量根本没法完整代表原文。
- 块不是越大越好，主要有三个坑：
  1. embedding model 最后要把所有 token 向量池化成一个向量。块越长，单一向量承载的语义点越多，表示就越"稀"，检索精度下降。
  2. Lost in the Middle：LLM 处理超长上下文时倾向于记住开头和结尾，中间的关键信息容易被淹没。
  3. 主题稀释：一个块塞了多个主题，查询命中其中任何一个主题的得分都会被其他内容拖低，导致召回失败。

我刚学分块时只记住了模型长度限制，后面两条一直没什么感觉。课程里那个鲁班七号的例子倒是让我记住了：把"技能、出装、背景故事"塞进同一个块，用户问"怎么出装"时，其他内容反而会把相关性得分拉低。

### Q2 🟢 RAG 常见的文本分块方式有哪些？每种的适用场景和优缺点是什么？

**参考答案要点：**

- 固定大小分块：按固定字符数或 token 数硬切，一般会留一点 overlap。它跑得快，块大小也好控制，拿来搭原型很方便；代价是完全不看句子和段落，切口落在哪里只能碰运气。
- 递归字符分块：按照段落、换行、句号、逗号、字符的顺序逐级往下切，尽量保住完整句子。普通文档先用它通常不会错，不过它认的是分隔符，不是语义。
- 基于文档结构分块：Markdown 按标题层级，HTML 按标签，代码按函数或类。文档结构靠谱时，这种切法又干净又省事；原始文档标题乱、层级缺失，它也跟着失灵。
- 语义分块：把句子转成向量，在相似度明显跳变的位置切。它适合结构混乱、按规则总切得七零八落的长文本，但每句话都要经过 embedding model，成本不低。面对整理得很好的 Markdown，它未必比按标题切得好。
- 父子分块（parent-child，也叫小块检索、大块返回）：先切父块，再在父块里切更小的子块；检索匹配子块，命中后把父块交给生成模型。这样不必在检索精度和上下文完整度之间硬选一个，只是要多维护一层父子映射。严格说它已经不只是分块，句子窗口检索也走的是相近思路。

我实际项目里的选择顺序是：先看文档有没有天然结构，Markdown、代码这种有结构的直接按结构切；没结构再上递归字符分块当兜底；这两样都不理想、块切得实在乱，才考虑上语义分块。别一上来就追最花哨的方法，大部分情况递归字符分块加合适的 overlap 就够用了。

### Q3 🟢 固定大小分块和递归字符分块有什么区别？chunk_overlap 是干嘛的？

**参考答案要点：**

- 固定大小分块（LangChain 的 `CharacterTextSplitter`）按单一分隔符（默认 `\n\n`）切段落再合并，遇到超过 chunk_size 的超长段落只能发个警告然后原样保留。
- 递归字符分块（`RecursiveCharacterTextSplitter`）持有一组有优先级的分隔符（段落 → 换行 → 句号 → 逗号 → 空字符），切出来的片段还超长就换下一级分隔符继续切，直到满足大小要求。
- chunk_overlap 让相邻块之间保留一段重叠内容，缓解在边界处把一句话的语义拦腰切断的问题。

有个地方很容易说错：LangChain 的 `CharacterTextSplitter` 并不是严格按固定长度硬切。它优先保持段落完整，只在累积长度超标时才结块，课程里管这叫"段落感知的自适应分块"。

另外中文场景记得提一句：默认分隔符里没有中文标点，得自己把 `。` `，` 加进 separators，不然切出来很难看。这个坑我第一次跑中文语料时实打实踩过。

### Q4 🟡 语义分块（Semantic Chunking）的原理是什么？什么场景值得用？

**参考答案要点：**

- 它在语义主题明显跳变的地方切分，而不是按字符数或分隔符下刀。
- LangChain 的 `SemanticChunker` 会先断句。每个句子连同前后 `buffer_size` 个句子一起做嵌入，再计算相邻向量的余弦距离。距离超过阈值的位置就是断点，最后按这些断点合并成块。默认的 percentile 法取第 95 百分位，只有最明显的 5% 语义跳变会触发切分。
- 断点识别还有标准差法、四分位距法、梯度法几种。梯度法适合句间语义联系普遍紧密的文本，比如法律、医疗文档。
- 代价：每个句子都要过一遍 embedding model，成本比规则分块高一个量级。语料结构混乱、规则分块切得稀碎的时候才值得上。

我一开始以为语义分块就是"让 LLM 帮忙断句"，其实完全不是，它是纯统计方法，不调用生成模型。另外别迷信它。课程作业里我拿结构良好的 Markdown 文档对比过，按标题层级切（`MarkdownHeaderTextSplitter`）又快又好，语义分块反而没什么优势。文档本身有结构就用结构，没结构再考虑语义分块，这个顺序别搞反。

### Q5 🟡 chunk_size 到底怎么选？有没有推荐值？

**参考答案要点：**

- 没有万能值，得看语料和查询模式：
  - 上界由 embedding model 的上下文窗口锁死；
  - 事实型短问答问题偏小块（检索准），总结型问题需要大块（上下文全）；
  - 最后还是要搭一套检索评估集，用 Recall@k / MRR 横向比较几组 chunk_size，别靠肉眼挑一个数。
- 也可以绕开这个两难：用小块检索，再返回较大的上下文。LlamaIndex 的句子窗口检索和父子块检索都属于这类 small-to-big 设计。

我以前也张口就报 512，后来换一批语料，这个数马上不好使了。块大了会稀释语义，块小了又缺上下文，所以现在我会先看文档和问题长什么样，再拿评估集试几组值。句子窗口和父子块也是从这个麻烦里长出来的。

## 二、向量嵌入

> 对应章节：[第三章第一节 向量嵌入](../../docs/chapter3/06_vector_embedding.md)

### Q6 🟡 embedding model 是怎么把一段话变成一个向量的？为什么长文本会"语义稀释"？

**参考答案要点：**

- 三步：分词 → Transformer 为每个 token 生成向量 → 池化（Pooling）把所有 token 向量压成一个向量。池化方式常见有取 `[CLS]` 位向量、mean pooling 等。
- 稀释的根源就在池化这步：一个 768 维向量要概括整块文本的所有信息，文本越长语义点越多，压缩损失越大，向量就越"平均"、越没有区分度。
- 这也是分块环节"块不宜过大"的底层原因，两道题是同一件事的两面。

我最初只记住了"长文本会稀释语义"，却解释不出为什么。后来把 pooling 这一步和 Q1 的分块问题连起来，才算把这件事想通。

### Q7 🟡 余弦相似度、点积、欧氏距离，检索时该用哪个？

**参考答案要点：**

- 余弦看方向不看长度，点积同时受方向和模长影响，欧氏距离度量绝对位置差。
- 向量做过 L2 归一化后，余弦相似度和点积等价，欧氏距离也和它们单调一致，选谁排序结果都一样。很多 embedding model（比如 bge 系列，encode 时设 `normalize_embeddings=True`）会输出归一化向量，配合内积（IP）索引用。
- 实践中跟着 embedding model 的官方文档走就行，模型训练时用什么度量就用什么，别自作主张换。

我曾经在归一化向量上纠结"用 COSINE 还是 IP"半天，后来才想通两者此时根本等价，纯属白纠结。但反过来，向量没归一化就用 IP，模长大的文档会天然占便宜，这个坑是真的。

## 三、向量数据库与索引

> 对应章节：[第三章第三节 向量数据库](../../docs/chapter3/08_vector_db.md)、[第五节 索引优化](../../docs/chapter3/10_index_optimization.md)

### Q8 🟢 MySQL 和 Elasticsearch 有什么区别？在 RAG 里 Elasticsearch 能干什么？

**参考答案要点：**

- 定位不同：MySQL 是关系型数据库，面向事务和结构化数据的增删改查；Elasticsearch 是分布式搜索引擎，面向全文检索和相关性排序。
- 索引结构不同：MySQL 用 B+Tree，擅长精确匹配和范围查询，`LIKE '%关键词%'` 这种中缀模糊匹配会退化成全表扫描；ES 用倒排索引，先分词再建"词 → 文档列表"的映射，全文搜索天然快，而且自带 BM25 相关性打分，结果是按"多相关"排序的，不是简单的匹配/不匹配。
- 一致性与事务：MySQL 支持 ACID 事务，适合当业务数据的真相源（source of truth）；ES 是近实时（写入后默认 1 秒左右才可搜）、无事务，定位是从主库同步过来的"检索视图"，两者常见的搭配是 MySQL 存、ES 搜。
- 回到 RAG：ES 就是混合检索里那路稀疏/关键词检索的典型承载者（BM25），新版本也支持 dense_vector 字段做 kNN 向量检索，所以很多团队直接拿 ES 一套搞定关键词+向量两路。

MySQL 和 ES 看着像传统后端知识，放进 RAG 以后，重点就变成它们各自站在哪一段。我会先讲 B+Tree 和倒排索引，再落到 ES 承担的关键词检索，后面正好接上 [Q14](#q14--混合检索已经拿到了两路结果为什么还要用-rrf-融合融合有什么好处)。

### Q9 🟢 为什么不直接拿 MySQL/PostgreSQL 存向量做检索？向量数据库到底解决了什么问题？

**参考答案要点：**

- 区别在查询模式上：传统数据库做的是精确匹配（B-Tree、哈希索引，"等于/大于/LIKE"），向量检索做的是"找最相似的 k 个"，暴力扫描是 O(N) 次高维距离计算，数据量一上来就不可用。
- 向量数据库主要靠 ANN（近似最近邻）索引解决这个问题：HNSW、IVF 这类结构用一点精度换几个数量级的速度，能在数十亿向量里做到毫秒级查询。
- 另外还有向量+标量的混合过滤、元数据管理、分布式扩展这些工程能力。

pgvector 这类扩展也让传统数据库有了向量检索能力，小规模（百万级以内）完全够用。要不要独立向量库，还是得看数据规模和运维成本，不是非黑即白。

### Q10 🟡 HNSW 和 IVF 的原理分别是什么？怎么选？

**参考答案要点：**

- HNSW（分层可导航小世界图）：基于图的方法。多层跳表式的邻近图，上层稀疏用来快速定位区域，下层稠密用来精确逼近，查询是贪心地逐层往目标"跳"。查询快、召回高，但图结构全在内存里，内存开销大。
- IVF（倒排文件索引）：基于聚类的方法。先把全库向量聚成 nlist 个簇，查询时只在最近的 nprobe 个簇里搜。省内存，常与乘积量化（Product Quantization）组合进一步压缩，但召回率对 nprobe 敏感，簇边界附近的近邻容易漏。
- 内存充足、查询性能优先时，我会先看 HNSW；数据量很大又卡内存，才更偏向 IVF 加乘积量化。两边都有拿召回率换速度的参数，最终还是得在自己的数据上跑 recall-QPS 曲线。

我一直拿"逛商场找店"打比方：HNSW 是先看楼层索引图再逐层下楼，IVF 是先决定去哪几个区再挨家看。不一定严谨，但面试时讲个直觉图景比干背参数强，被追问细节再上 nlist/nprobe、efSearch 这些参数不迟。

### Q11 🟢 常见的向量数据库有哪些？使用场景和优缺点怎么对比？

**参考答案要点：**

- FAISS：严格说是向量索引库不是数据库，没有服务层、元数据管理和增删改查，要自己包一层。胜在性能强、索引类型全（还有 GPU 加速），适合研究实验和自建检索引擎的团队。
- Chroma：轻量嵌入式，pip 装完几行代码就能跑，元数据过滤、持久化都有，原型和中小项目的首选。数据量到千万级以上或需要分布式时会吃力。
- Milvus：生产级分布式方案，十亿级向量、标量过滤、多种索引、混合检索都支持。代价是架构重（依赖 etcd、MinIO 这些组件），部署运维有门槛；轻量场景可以用 Milvus Lite 过渡。
- Pinecone：全托管 SaaS，零运维、开箱即用、弹性伸缩，适合不想养基础设施的团队。缺点是持续付费，数据放在第三方，合规敏感的业务过不了审。
- pgvector / Elasticsearch：不是专职向量库，而是在已有数据库/搜索引擎上加向量能力。数据量不大（百万级）、又不想多维护一个组件时非常务实，还顺手解决了向量和业务数据的一致性问题。
- 选之前先问数据规模（百万还是十亿）、有没有人运维、数据能不能出内网、要不要和现有技术栈整合。限制条件摆出来以后，通常不会剩下太多选项。

我现在不会先背一遍工具清单，而是先把项目的限制条件摆出来，再看哪个工具能留下。pgvector 也别急着排除，我见过向量库选得很高级，最后却在业务库同步上吃尽苦头。课程主线用 Milvus，自己跑 demo 时换成 Chroma 或 Milvus Lite，反而省心。

### Q12 🟡 文档数量到了百万级该怎么办？MySQL 怎么存？存储和检索压力大了又怎么扛（不换 ES 的情况下）？

**参考答案要点：**

- 先算 chunk，不要只看文档数。百万篇文档切完很可能变成千万个 chunk，向量数量、维度和并发量比“百万”这个数字更能说明压力。这个规模有时单机就够，有时也会吃紧，得先算内存和 QPS。
- 表可以拆成文档表和 chunk 表：前者放 doc_id、标题、来源、时间，后者放 chunk_id、doc_id、正文和向量。MySQL 负责原文与元数据，向量检索交给 HNSW/IVF，两边用 chunk_id 对上。把向量序列化成 BLOB 或 JSON 只是存进去了，MySQL 没有原生 ANN 索引，直接算相似度还是全表扫。
- 存储里最占地方的是向量，百万个 768 维 float32 已经接近 3GB。乘积量化（Product Quantization）或 int8 能继续压缩；正文可以去重，冷数据放到便宜存储。再往上长，才考虑按 doc_id 或时间拆分。
- 检索侧先保证不用暴力扫描。内存紧可以选 IVF 加乘积量化，查询前能按租户、时间等元数据过滤就先过滤。MySQL 的读压力再用读写分离和缓存处理；ANN 服务顶不住时，再做水平扩容和索引分片。
- 百万级下，MySQL 当存储真相源、单机 HNSW 当检索层通常够用。存储压力靠量化和分库缓解，检索压力靠索引、缓存和预过滤处理；到了十亿级或高并发，再考虑拆服务和分布式索引。

我以前一听"百万"就想上 Milvus 集群，后来算了下向量数量和内存，发现离非拆不可还早。把 MySQL 和向量索引的职责分开以后，存储和检索各自该怎么优化也清楚多了。

## 四、混合检索

> 对应章节：[第四章第一节 混合检索](../../docs/chapter4/11_hybrid_search.md)

### Q13 🟢 关键词检索和语义检索有什么区别？各自适合什么场景？

**参考答案要点：**

- 一个认字，一个认意。关键词检索（BM25/倒排索引，背后是稀疏向量）把文档当词的集合，查询里的词在文档里出现了才算数；语义检索（embedding model + 向量检索，背后是密集向量）把查询和文档都映射到语义空间，比的是意思像不像。
- 关键词检索精确、好解释，也不用训练模型。BM25 里 k1 控制词频饱和度，b 负责文档长度归一化。它的问题是认词不认意思，不知道"西红柿"和"番茄"说的是一回事。
- 语义检索能接住同义改写和口语问题。搜"蛋白质丰富的家常菜"，原文里即使没有这几个字，也可能捞到"西红柿炒蛋"。但向量为什么相似很难解释，embedding model 还要付出推理成本；错误码、产品型号这种没见过的字符串，它经常处理不好。
- 各自的主场：
  - 关键词检索赢在"必须一字不差"的场景：产品型号、错误码、函数名、法条编号。用户搜 `ERR_CONN_RESET`，语义模型给你召回一堆"网络连接异常的常见原因"，就是不给带这个错误码的那篇，这时候关键词一发入魂。
  - 语义检索赢在"用户不知道文档怎么写"的场景：客服问答、知识库搜索。用户用自己的话问，文档用作者的话写，中间隔着的那层表述差异只有语义能跨过去。
- 所以实际系统里很少硬选一边，通常让两路各找各的，再合并结果。

我自己的记法是把它俩想成两个图书管理员：一个只查书名卡片，你报错一个字他就两手一摊，但报对了秒给；另一个读过馆里所有书，你含糊地描述个大概他也能懂，但偶尔自作聪明拿错。真实系统就是把俩人都雇了，各干各的活。

### Q14 🟢 混合检索已经拿到了两路结果，为什么还要用 RRF 融合？融合有什么好处？

**参考答案要点：**

- 混合检索只是让 BM25 和向量检索各自查一次，拿到的是两张独立的候选列表，还不是一张能直接交给下游的最终排名。简单拼接会有重复文档，也说不清 BM25 第 1 名和向量检索第 1 名谁该在前面。
- 两路分数不能直接比较。BM25 可能打出十几分，余弦相似度通常落在 0 到 1 附近，数值大小和分布都不同。直接相加时，数值范围更大的那一路很容易把另一条路淹没；先归一化也会引入额外规则，而且换一批数据，分数分布可能又变了。
- RRF 把各路原始分数换成排名再合并，不要求两套检索器使用相同的打分尺度，也不用专门训练一个融合模型。接入新的检索通道时，只要它能返回有序列表，就能一起参与融合。
- 同一篇文档如果在 BM25 和向量检索里都靠前，会吃到两路加分；只被其中一路捞到的文档也不会直接出局。这比给两路硬分配固定名额灵活。
- 合并时还会去重，最终只给下游一张候选表。不过 RRF 仍然是粗排：它只看名次，不会细读查询和文档，也看不出第 1 名究竟比第 2 名高多少分。头部精度不够时，还得接 Cross-Encoder。

我最开始做混合检索，就是把两路 top 10 拼起来再去重。结果谁先拼谁总在前面，调换一下代码顺序，最终答案都可能跟着变。换成 RRF 后至少有了一把两边都认的尺子：两路都看好的文档往前排，单路捞到的也不会被扔掉。至于 RRF 具体怎么算，就是下一题的内容。

### Q15 🟡 RRF 是怎么融合多路检索结果的？为什么用排名而不用原始分数？

**参考答案要点：**

- 公式：RRF_score(d) = Σ 1/(rank_i(d) + c)，对文档在每一路检索结果里的排名取倒数再求和，常数 c 通常取 60。
- 用排名不用分数的原因：BM25 分数和余弦相似度根本不在一个量纲上，一个可能是 15.7 一个是 0.83，直接加权毫无意义，要么先做归一化（而归一化方式本身又引入新的超参和分布假设）。排名天然可比，绕开了整个问题。
- c 的作用：压制排名极靠前的文档的相对优势。没有 c 的话第 1 名得分是第 2 名的两倍（1 vs 0.5），有了 c=60 之后是 1/61 vs 1/62，差距变得平缓，融合更稳健，不至于被单路检索的头名绑架。

坦白说，"为什么用排名"这一问我第一次被问时答崩了，只会说"因为论文里这么写"。后来自己拿 BM25 和向量分数各打印了一遍才直观感受到量纲差多远。c 的作用也建议自己代几个数算一下，算过一次就再也忘不掉。

## 五、重排序

> 对应章节：[第四章第五节 检索进阶技术](../../docs/chapter4/15_advanced_retrieval_techniques.md)

### Q16 🟡 已经用了混合检索（BM25 + HNSW），为什么还要加重排？好处是什么？

**参考答案要点：**

- 混合检索管的是"候选够不够全"，重排管的是"前几名准不准"。前者靠关键词和语义两路互补，后者再从候选里挑出更贴近问题的内容。
- RRF 融合只用了排名信息，不会产生新的相关性判断。BM25 看词频，向量检索用 Bi-Encoder 分别编码查询和文档，整个召回阶段都没有把"查询+文档"放在一起细读。两个粗信号融合以后，仍然只是粗排。
- Cross-Encoder 会把查询和文档拼在一起做 token 级注意力交互，补上召回阶段缺少的成对判断。
- 重排后，相关文档更容易排到 top-k 前面，送进 LLM 的上下文也更干净。候选数量也可以顺手砍掉一些：先召回 50 条，重排后只留 5 条，既省上下文成本，也能缓解 Lost in the Middle。
- 代价是多一次模型推理和一套部署。QPS 高，或者当前头部结果已经够用时，不加重排也完全说得通。

刚看到这里时，我也觉得"都两路检索了还要啥自行车"。后来才想明白，RRF 只是把两份排名表拼起来，好比两个只扫了一眼简历的 HR 把意见平均了一下，仍然没人认真做过面试。课程实战篇停在 RRF，Cross-Encoder 补的正是这一步。

### Q17 🟡 Cross-Encoder 既然更准，为什么不直接用它做全库检索？

**参考答案要点：**

- 因为它的分数依赖"查询+文档"成对输入，查询来了才能算，没法离线预计算。全库 N 篇文档就要 N 次完整的 Transformer 前向，百万级文档等于每次查询跑一百万次 BERT，延迟完全不可接受。
- Bi-Encoder 的文档向量可以离线算好建索引，在线只做一次查询编码加 ANN 查找，这才撑得起大规模检索。
- 所以两者不是替代关系，是流水线上下游的分工关系。

Q16 再往下追，差别就落在"能不能离线预计算"上。Cross-Encoder 不是不准，而是算不起全库。

### Q18 🟡 混合检索（BM25 + HNSW）叠上重排后延迟明显变高，有哪些可行的优化手段？

**参考答案要点：**

- 先把查询嵌入、BM25、HNSW、RRF 和 Cross-Encoder 的耗时分别打出来。重排往往最慢，因为每个候选都要和 query 成对跑一次模型，但别没测就认定一定是它。
- 候选数通常最值得先试。top 100 全部重排和只排 top 20，耗时差得很直接，而最后送给 LLM 的可能只有 5 条。究竟能砍到多少，要拿评估集测，不能只看延迟。
- 模型侧可以换小一些的交叉编码器，比如从 bge-reranker large 换到 base；也可以转 ONNX / TensorRT，用 fp16 或 int8，再把候选组成 batch 上 GPU 推理。
- 热 query 可以缓存，两路召回应该并行。重排服务单独部署后，也更方便按压力扩容。
- 用轻量重排器做中间层：先用 ColBERT 这类后期交互模型把几百个候选粗排到几十，再用重的 Cross-Encoder 精排，用精度梯度换延迟。
- 实在没辙也可以异步：先拿召回结果快速出一版，重排在后台跑完再刷新，适用于对实时性没那么苛刻的场景。

我自己踩过的坑是一上来就换模型、上量化，结果 profile 一看，大头是候选数给得太多。把重排输入从 200 降到 40，延迟直接掉了一大截，效果却几乎没变。后来再碰到延迟问题，我都会先把各阶段耗时打出来。

### Q19 🟡 检索侧的评估指标有哪些？Recall@k、MRR、MAP 分别看什么？

**参考答案要点：**

- Precision@k：检索出的前 k 个里相关文档占比，看结果干不干净。
- Recall@k：前 k 个里找到的相关文档占全部相关文档的比例，看该找的有没有找齐。RAG 通常比较看重它，因为没被召回的知识，LLM 再强也无中生有不了。
- MRR：第一个相关文档排名的倒数取平均，适合"用户只关心第一个正确答案"的场景。
- MAP：对每个查询算平均精确率再取平均，同时反映精度和排序质量，是更综合的指标。
- 这些指标都依赖标注数据集（查询 + 真实相关文档）。没有标注就算不出来，而整理这套评估集往往比写计算指标的代码费事得多。

### Q20 🟡 RAG 检索的准确率怎么评估？具体怎么测试？

**参考答案要点：**

- 指标用 Q19 里的 Recall@k、Precision@k、MRR、MAP。麻烦的通常不是公式，而是手里有没有一套能反复跑的数据。
- 这套数据也就是 golden set：每条 query 都标出相关文档或 chunk，标成相关/不相关，或者再细分等级。人工标最踏实，也可以从真实日志抽 query；让 LLM 根据文档反向生成问题能省时间，但生成完必须抽查。
- 评测时只跑检索，记录每条 query 返回的 top-k 文档 ID，再和标注对比。生成模型先别接进来，否则答案变了，很难判断是召回波动还是 prompt 碰巧起作用。
- 我会把它写成回归脚本。chunk_size、embedding model、重排策略每改一次，就在同一批 query 上重跑，不然几轮参数调完，很容易只记得最后一次结果。
- 检索指标和最终回答质量分开看。前者用 Recall@k 这些指标，后者再看忠实度、答案相关性或 RAGAS。上线以后还要对照点击、人工反馈和 A/B 结果，离线分数高不等于用户一定满意。

我第一次做评估时偷懒，只看最终答案好不好。参数改了半天，结果变好究竟是检索有效，还是 prompt 赶巧，我自己都说不清。后来把检索单独拉出来，固定一套 golden set 做回归，问题才没再搅成一团。

### Q21 🟡 RAG 检索效果比较差，有哪些排查方向或手段？

**参考答案要点：**

- 我会先把送进 LLM 的上下文打印出来。相关文档不在里面，就查检索；文档已经在，回答仍然不对，再看 prompt 和生成模型。只盯最终答案，很容易把两类问题搅在一起。
- 然后回到数据源确认原文是否真的存在、是否成功入库。PDF 解析漏页、表格打散、权限过滤错了，都可能伪装成检索效果差。源头没有内容，后面换什么模型都找不回来。
- 分块环节：chunk 是不是切得太大导致语义稀释，或者太小导致上下文碎。中文语料还要看分隔符里加了中文标点没有，没加的话块会切得很难看。
- 向量化环节：embedding model 适不适配这个领域（通用模型碰到医疗、法律、代码这类专业语料容易拉胯）、中英文模型选对没、向量有没有归一化、query 和文档是不是用了同一个模型编码。
- 检索策略：只用向量检索时，产品型号、专有名词这类 query 容易漏，可以加 BM25 做混合检索；top-k 太小，相关文档可能进不了候选集；没有重排，头部排序也可能不准。
- 查询侧：用户 query 本身质量差（口语化、指代不清、太短），上查询改写 / HyDE / 多路分解；多轮对话还要先做指代消解。
- 排查出来的猜测要回评估集验证。准备 query 和相关文档标注，算 Recall@k，每轮只换一个变量；改动前后差多少，比凭感觉判断更可靠。

我习惯从送进 LLM 的上下文往回查，这一步便宜，而且一眼就能看出不少问题。以前我也会先换 embedding model、调 top-k，折腾半天才发现相关内容在解析时就丢了。现在先看上下文，再倒着查检索、分块和入库，少走很多弯路。

### Q22 🟡 评测发现召回率不达标，或者相关文档召回了但排名靠后，怎么优化？

**参考答案要点：**

- 先看相关文档到底去了哪里：扩大候选集仍然找不到，说明召回覆盖有问题；能找到但排在几十名以后，才是排序问题。我会让评测脚本把相关文档的名次、各路分数和融合后排名一起输出，平均 Recall@k 看不出这些细节。
- 完全没召回时先查数据和分块：目标内容有没有入库、解析时有没有丢、相关答案是不是被切断了。如果知识散在相邻块里，可以调小 chunk_size、增加 overlap，或者用父子分块，让更聚焦的子块参与检索。
- 内容在库里但候选集没有它，就动召回策略：增大 top-k；HNSW 调高 `efSearch`，IVF 调高 `nprobe`，用查询延迟换召回率；检查元数据过滤条件是否误杀；只有向量检索时补一条 BM25，专门兜产品型号、错误码和专有名词这类 case。
- query 和文档的说法差得太远时，可以做查询改写、Multi-query 或 HyDE。embedding model 跟领域不匹配，就换领域模型；有足够标注数据时，再用漏召回 case 和 hard negative 微调 embedding model。换模型后文档向量必须全部重建，不能只换 query 端。
- 相关文档能进候选集但排名靠后，优先加或调重排。用 Cross-Encoder 对候选集重新打分，通常比继续放大 top-k 更对症。已经有重排器的话，把这些低排名 case 做成正负样本继续训练，尤其要加入“看着很像但答案不对”的 hard negative。
- 混合检索还要分别看 BM25、向量检索和融合后的名次。某一路明明排得很高，经过融合反而掉下去了，就检查 RRF 参数或加权融合的权重，而不是去改 embedding model。不同类型的 query 也可以走不同权重，比如错误码偏 BM25，口语问法偏向量。
- 改动要在同一套 golden set 上重跑 Recall@k、MRR 或 NDCG，并按错误码、事实问答、长问题分桶看。总分上涨时也得回看原来的失败 case，有时大类样本涨得多，刚好把小类退化遮住了。这批 case 最后留在回归集里，免得下次又坏回去。

我以前看到 Recall@10 低，第一反应就是把 top-k 从 10 调到 50。数字确实好看了一点，可目标文档从第 18 名挪进候选集，最后照样进不了 LLM，上下文还平白多了四倍。后来把失败 query 一条条展开，才发现有的是中文简称没匹配上，有的是正确块被相似但答非所问的块压住了。前一种补 BM25，后一种交给重排器，比一起拧 top-k 靠谱得多。

### Q23 🟡 top-k 设为 20，但最关键的信息恰好排在第 21 位，怎么解决？

**参考答案要点：**

- top-k 只是一条截断线，不承诺最相关的信息一定在线内。第 21 位说明检索器找到了这个块，只是它没能进入交给下游的候选集。先对比 Recall@20、Recall@50 和相关文档的排名分布，看看只是这一条擦边，还是很多答案都堆在 20 名以后。
- 可以把召回池扩大到 50 或 100，但没必要全塞给 LLM。“召回多少条”和“最终给多少上下文”应该是两个参数：先召回 50 条，经过 RRF 和 Cross-Encoder 后只留前 5 到 20 条。第 21 名有机会翻上来，上下文却不会跟着翻倍。
- 扩大候选池以后，关键块如果仍然靠后，就该查排序了。分别看它在 BM25、向量检索和 RRF 后的位置，再决定是改查询、改分块、换 embedding model，还是拿 hard negative 训练检索器和重排器。
- ANN 索引也可能在近似搜索时漏掉本该靠前的向量。HNSW 可以调高 `efSearch`，IVF 可以调高 `nprobe`，用一部分延迟换更完整的候选集。这和扩大 top-k 不是一回事：top-k 决定返回多少条，`efSearch`、`nprobe` 决定搜索过程看得够不够广。
- 也可以按需扩大候选池：先取 20 条，头部相关性都很低或证据不足时，再取 50 条重排。这样比每次固定取 100 条省资源，不过触发条件得拿评估集校准，不能随手拍一个阈值。
- 如果某类关键信息必须保证找到，比如合规条款、产品型号或租户范围，别只赌向量相似度。可以先用元数据过滤、关键词精确匹配或规则路由缩小范围，再做语义检索。检索系统只能提高概率，单纯把 top-k 一直调大，换不来绝对保证。

把 20 改成 21 只能救这一条 case，下一条可能卡在第 51 位。我会把召回池适当放宽，再让重排决定谁进上下文。重排后还是上不来，就回头修检索；继续往 prompt 里堆材料只会把问题盖住。

### Q24 🟢 用户的原始查询经常质量很差，有哪些查询改写手段？

**参考答案要点：**

- Multi-query（多查询分解）：让 LLM 把一个问题改写/拆解成多个角度的子查询，分别检索再合并结果，提升召回覆盖面。
- Step-Back Prompting（退步提示）：把具体问题抽象成一个更泛的背景问题先检索。比如"1954 年爱因斯坦在做什么"退一步成"爱因斯坦的生平经历"，专治原始问题太具体导致检索不到的情况。
- HyDE（假设性文档嵌入）：让 LLM 先凭空写一篇假设性的答案文档，拿这篇假文档的向量去检索。原理是"文档和文档的相似度"通常比"短查询和文档的相似度"更好算，假文档就算细节全错，风格和用词也更接近真实文档。
- 查询路由：先判断该查哪个数据源/走哪条链路，再分发。

第一次看到 HyDE，我的反应是"用幻觉打败幻觉？"，觉得很邪门。后来想通了：检索匹配的是语义空间里的位置，假文档哪怕内容错了，只要用词和答案接近，就可能帮上忙。专业领域就不一定了，LLM 编得越偏，检索也会跟着跑偏。

### Q25 🟡 什么是 Agentic RAG？它和传统的固定 pipeline RAG 差别在哪？

**参考答案要点：**

- 传统 RAG（包括 Naive 和大多数 Advanced RAG）是条固定流水线：检索 → 拼上下文 → 生成，一遍过，检索得再烂也照样生成。
- Agentic RAG 把 LLM 放到调度位置上，让它自主决策：要不要检索、检索什么、用哪个数据源、检索结果够不够好、不够好就改写查询再来一轮。检索从"固定步骤"变成了 Agent 手里的一个"工具"。
- 它可能做查询路由，决定走向量、关键词还是图检索；也可能检查召回结果，不满意就改写后重试。碰到多跳问题时，后一轮查询还会依赖前一轮拿到的信息。课程第九章的智能路由就是一个现成例子。
- 每多一个决策点，往往就多一次 LLM 调用，延迟和费用都会涨，系统里还多了一个"Agent 判断错了"的故障入口。简单问答硬套 Agentic，通常不划算。

我觉得这个词已经被用得有点泛了，很多所谓 Agentic RAG 只是加了一层 if-else 路由。判断它算不算 Agentic，与其数名词，不如看哪些决策原来写死在代码里，现在交给了模型，以及模型判断错了以后系统怎么收场。

### Q26 🟡 多轮对话场景下，用户的后续问题（比如"那它的缺点呢？"）怎么检索？

**参考答案要点：**

- 这里卡在指代消解。"它"单独放进向量空间几乎没有可用信息，直接检索很容易跑偏。
- 可以把对话历史和当前问题一起交给 LLM，改写成一个自包含（self-contained）的问题。比如把"那它的缺点呢"还原成"HNSW 索引的缺点是什么"，再拿完整问题检索。
- 实现上有两个细节：改写用的 LLM 可以是个小模型（任务简单），别拿主力模型烧钱；对话历史太长要做截断或摘要，不然改写本身也会被带偏。
- 改写错了，后面的检索和重排都会跟着跑偏。线上最好保留改写前后的 query，定期抽样检查。

我做教程 demo 时一直用单轮问题，接进聊天界面后才发现用户根本不会每次都把主语说全。"那它呢"这种半句话，才是多轮产品里的日常。

## 如何贡献新题

攒题库这种事，一个人闭门造车肯定不行。如果你也在学这门课或者刚面完试，欢迎把你遇到的题补进来。几个约定：

1. 按上面的知识点分类放，找不到合适分类就新开一节
2. 标注难度（🟢/🟡），能关联课程章节的加上相对路径链接
3. 参考答案写要点，别一句话糊弄，也别贴一整篇论文
4. 提 PR 前搜一下有没有重复的题，相似的题可以合并成一题多个追问
5. 最重要的：写下你自己对这道题的理解，哪怕是"我也没完全搞懂 X 部分"。答案网上到处都是，个人的思考过程才是这个题库区别于搜索引擎的地方

题目来源建议注明（自己被面到的 / 面经看到的 / 从课程内容反推的），方便后人判断题目的真实出现频率。
